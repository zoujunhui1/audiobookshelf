# Go 登录重写与 Node 联合运行：人机协作报告

记录日期：2026 年 10 月 12 日。时间统一采用 Pacific/Auckland（UTC+13）。

## 一、开发目标与范围

本次开发将 Audiobookshelf 的用户名密码登录迁移到 Go，同时保留 Node.js 后端处理其他功能。前端继续使用原有请求与响应约定，两个后端共享现有 SQLite 数据库。

工作包括：

- 实现 Go 反向代理，将未手动注册的请求转发到 Node，并返回 Node 的响应。
- 实现 Node 进程管理：就绪检查、按需启动、并发启动去重、退出后重启及关闭时的进程清理。
- 手动注册 `POST /login`，按 Router → Handler → Auth Service → DB 分层处理登录。
- 读取现有用户和密码哈希，校验 bcrypt 密码、用户启用状态及本地认证配置。
- 签发与 Node 兼容的访问令牌和刷新令牌，将刷新会话写入共享数据库。
- 检查数据库连接有效性并在失效时重连，配置 WAL、锁等待与外键。
- 编译、运行自动化测试，并使用真实 Node 后端完成联合测试。

## 二、人和 AI 的协作方式

采用“人指定目标和分层，AI 阅读代码、实现并验证，人持续提问和推进下一步”的协作方式。

| 参与方 | 本次承担的工作 |
| --- | --- |
| 人 | 提出 Go 与 Node 共存的目标；询问请求格式、SQLite 并发和身份验证机制；指定 `proxy/forward.go`、`proxy/node.go`、`handlers/login.go`、`services/auth.go`、`db/read.go`、`db/manager.go` 的职责；要求真实后端联调与中文报告。 |
| AI Agent | 阅读现有 Go 骨架与 Node 认证实现；解释技术方案；修改代码、配置和 README；准备临时工具链及依赖；编写测试；运行编译、竞态检测和真实后端联调；检查日志并修复问题。 |

开发按两个实现阶段推进。首先完成默认代理和 Node 生命周期管理；随后接管登录，增加密码验证、令牌生成和会话持久化。用户在代理实现过程中插入身份验证问题，Agent 在同一执行回合中回答后继续开发。

兼容性是共同约束：Go 使用 Node 原有的用户表、`pash` 密码字段、JWT 密钥和会话结构。为保留前端需要的权限、书签、播放进度及服务器设置，Go 用新签发的访问令牌调用 Node 的 `/api/authorize` 补充响应数据；提交的用户名和密码不发送给 Node。

AI 在执行中发现并修正了两类问题：

- 最初误将 `EXP_PROXY_SUPPORT=1` 用作反向代理配置；检查实际 Node 代码后发现该设置会关闭 SSRF 请求过滤，随后移除，并重新验证。
- 测试工具最初使用的 Gin 响应记录器与代理旧式关闭通知不兼容，进程计数也只检查了 Go 的主线程；分别改为真实 HTTP 请求和统计所有 OS 线程的子进程。修正后测试通过。

## 五、重写效果

### 已实现的行为

| 项目 | 结果 |
| --- | --- |
| 路由分工 | Go 处理 `GET /health`、`POST /login` 及配置前缀下的登录；其余请求转发到 Node。 |
| 请求和响应兼容 | 保留业务请求的路径、查询参数、请求体、认证头、Cookie、响应状态和内容；支持流式响应与 WebSocket 升级。 |
| Node 生命周期 | 首次需要时启动；并发请求共用一次启动；退出后按需重启；Go 关闭时清理自己启动的进程，保留外部启动的 Node。 |
| 登录认证 | Go 查询共享数据库，校验用户名、bcrypt 密码、用户启用状态和本地认证配置。支持原有无密码 root 行为。 |
| JWT 兼容 | Go 生成 HS256 访问令牌与刷新令牌，复用 `JWT_SECRET_KEY` 或数据库中的 `tokenSecret`。 |
| 会话兼容 | Go 写入 Node 原有会话表；Node 可以继续刷新令牌、退出登录并验证业务 API 与 Socket.IO 身份。 |
| 数据库管理 | 每次访问检查文件及连接；失效时重连；使用单连接、WAL、5 秒锁等待和外键。Node 继续负责数据库初始化与迁移。 |
| HTTP 登录行为 | 支持 JSON 和表单；错误请求返回 400，认证失败返回 401，限流返回 429，服务不可用返回 503。兼容浏览器刷新 Cookie 和移动端令牌返回方式。 |

### 验证结果

- Go 编译成功，最终 `go test -race ./...` 全部通过。
- 代理阶段完成 **21 项真实 Go + Node 联调检查**。
- 登录重写后，设置环境变量密钥和复用数据库密钥两种配置各完成 **28 项检查**，共 **56 项次**；这是同一组场景的两次运行，不是 56 个不同场景。
- 联调覆盖自动启动、8 个并发首次请求、原有路由前缀、初始化、登录、错误密码、大小写用户名、缺失字段、表单格式、SQL 注入式用户名、Cookie、API 鉴权、浏览器与移动端刷新、退出、Socket.IO、停用用户、WAL、重启和进程清理。
- 自动化测试还覆盖无密码 root、长密码兼容、数据库连接恢复、缺失数据库不被新建、禁用本地认证、失败登录不产生孤立会话，以及请求格式和限流。

真实联调使用临时 SQLite 和独立端口，未修改现有业务数据库。测试结束后已关闭测试进程。

### 当前范围与限制

用户名密码校验、令牌生成和会话创建已迁移到 Go，但完整登录响应仍依赖 Node 的 `/api/authorize`。刷新、退出、OpenID 和其他业务功能继续由 Node 提供，因此当前是两个后端协作运行的登录切片。

本次未进行浏览器页面端到端测试、媒体播放测试、吞吐量或延迟基准测试。联调跳过 ffmpeg/ffprobe 检查，因此只能确认已覆盖的路由、认证和会话行为正常，不能据此声称性能提升或全站完全兼容。SQLite 驱动使用 CGO，构建需要 C 编译器。
